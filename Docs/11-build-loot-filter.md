# Build 过滤器

[返回项目说明](../README.md)

过滤器从公开 Build 提取需求，不需要上传存档。存档同步流程、世界编辑与物品编码保持独立。

## 五步确认

1. 需求暗金：按身份选择暗金，套装单列，可搜索补充过渡目标。
2. 高价值词缀：从装备实际附加词缀初始化，可增删；神像按形状独立维护前后缀需求。
3. 有效词缀：通用生命、耐伤、护盾、属性、抗性、护甲、防御与功能词缀默认勾选。高价值词缀同样有效，在合并集合中只计一次。
4. 隐藏类型：逐项或按装备家族选择装备类型，按职业或逐底材选择神像，也可隐藏整个神像形状。默认不隐藏任何类型。
5. 分组与导出：调整显示／隐藏、颜色与强调，预览并下载原生 XML。

## 四类普通装备

令 H 为高价值词缀，U 为高价值与其余有效词缀的并集。仅统计实际存在的所选词缀，不给无效词缀或空槽扣分。

| 优先级 | 固定分组 | 条件 |
| --- | --- | --- |
| 1 | 核心词缀崇高装备 | 崇高，至少一条 H 达到 T6 |
| 2 | 有效词缀崇高装备 | 崇高，至少一条 U 达到 T6，且至少三条 U |
| 3 | 考虑打造装备 | 至少两条 U 达到 T5，且至少一条 H 达到 T5 |
| 4 | 开荒过渡装备 | 至少一条 H，且至少三条 U，不限层级 |

T6/T7 为同一档，T8 也满足 T6 条件；T5 条件包含更高层级；T4 及以下由不限层级规则处理。高优先级先匹配，隐藏同样终止匹配。四类分组不能添加、删除、改名或配置门槛。未匹配的普通、魔法、稀有与崇高装备使用一条默认隐藏的兜底，不作为第五个可配置装备类别。

每类仅生成一条原生 Rule，使用包含装备类型 0–24 的一个 SubTypeCondition。多个词缀 ID 共享 AffixCondition，多个条件取 AND。空词缀池和原生编辑器会钳制的不可满足计数不会生成宽泛规则。典型公开 Build 的四类装备为四条，总计 25 条规则。

## 隐藏装备与神像

玩家明确选择的隐藏规则优先级最高，包括该类型的需求暗金、套装与其他保留目标。装备类型和完整神像形状合并成一条多类型隐藏规则。精确神像底材按形状分别生成单类型规则，再填写 subTypes；原生多类型条件不使用精确 subTypes。整形状已隐藏时省略重复底材规则。资源和祭坛不在此页的选择范围内。

“隐藏其他职业神像”读取当前 Build 的职业与目录 classRequirement 位标记：野蛮人 1、法师 2、哨卫 4、侍祭 8、游侠 16；Build 职业索引为 0–4。普通、异端与预兆底材使用同一判定，不按名字猜测。法师会选择其他职业的 48 个底材，保留法师 12 个及通用 13 个。初始没有自动排除双手武器或任何神像。

## 身份、特殊词缀与安全兜底

需求分析读取普通词缀、封印、腐化与原初附加字段；固有 ir/ur 不加入价值池。暗金 fixed variant 根据 game-item-data.json 的 specificAffixIds 归入 inherentAffixes；同一腐化词缀在其他装备上的真实附加仍可有效。真实原初词缀需要 T8。封印等额外词缀参与有效数量统计。

未解析目标或版本不匹配会把其他装备、其他神像兜底改为显示，并阻止严格兜底隐藏。用户明确选择的类型隐藏仍按其选择执行。暗金相对稀有度基于随机池 rerollChance，不代表 Boss 掉率或市场价格。需求身份、神像配对、资源和祭坛的规则保持各自范围。

切换阶段、语言和返回同一 Build 保留草稿；导入另一 Build 重建草稿。只有语言偏好持久保存。schemaVersion 为 3，四类规则不再使用计分编译器或近似结果。导出遵循原生 Order 顺序与 XML 转义，规则上限仍为 200。

## 验证

运行 npm test 和 npm run build。固定规则边界测试与独立 XML 条件解释器检查 T1–T8、有效数量、所有装备类型、额外词缀、隐藏优先级、精确神像底材、特殊暗金来源及资源隔离。交互测试覆盖五步切换、选择保持、固定分组和颜色预览。依赖锁检查在 npm ci 前执行，避免缺失版本的可选平台依赖进入构建。
